# PRACTIS — Codebase Audit (2026-09-30)

**Method:** static read of every source file (3,235 LOC), plus **empirical proof-of-write probes**
against a throwaway temp DB — an HTTP 302 was never accepted as evidence; every claim below is
backed by a measured row count before vs after.

**Scope:** `src/` (23 files), `views/` (20 files), `db/migrations/001–009`, `test/` (10 files,
148 tests). Read-only w.r.t. the repo; probes ran on temp databases only.

**Baseline at audit time:** HEAD `9d069e9`, tree clean, DB v9 `integrity ok`, **148/148 tests pass**.

---

## Verdict

The **data model is genuinely strong** — money invariants, immutability and audit are enforced by
DB triggers rather than convention, and that is the hardest thing to retrofit. The
**web layer is one authorization pass away from being unsafe**: five mutating routes that write
money accept *any authenticated user*, including a read-only Viewer. This is not theoretical; it was
executed and the rows are in the database.

The reason it survived 148 passing tests is a **test-strategy gap, not carelessness**: the suite
verifies *authentication* (anonymous is blocked) but almost never *authorization* (wrong role is
denied). Only `admin.test.js` tests a capability boundary.

## Blockers

### B1 — The ledger is writable by any authenticated user

`src/routes/app.js:88` `POST /ledger/entry` and `src/routes/app.js:187` `POST /ledger/:id/reverse`
have **no capability guard**. Every other domain route in the app has one
(`/advances`, `/expenses`, `/reconciliation` are all `requireCapability`-gated), so this is an
omission, not a design choice.

**Proven:** demoting the seeded user to `role_code='viewer', is_system_admin=0` and posting:

```
[1] POST /ledger/entry as Viewer -> HTTP 302
    ledger rows: 6 -> 7   *** WRITE SUCCEEDED ***
    inserted: {"id":7,"amount":777000,"description":"viewer injected cost",...}
[2] POST /ledger/1/reverse as Viewer -> HTTP 302, loc=/ledger?reversed=8
    reversals of line 1: 1  *** WRITE SUCCEEDED ***
```

**Why this is the worst of the five:** a reversal is **irreversible**. `idx_ledger_one_reversal`
enforces *a line is reversed exactly once*, and PRD §8 says *"Never: delete Finance-entered
entries (immutable)"*. A Viewer clicking Reverse on a real cost line permanently consumes that
line's single correction slot. The only remedy is a further reversing entry — the books can be
churned indefinitely by the least privileged role in the system, each churn an audited but
legitimate-looking posting.

### B2 — Cost tagging / the checker's *final* check is reachable by any authenticated user

`src/routes/app.js:259` `POST /queue/tag` has **no capability guard**. This single route does the
**Cost Controller's** job: it assigns the CBS account and sets `cost_checked = 1`.

**Proven:**

```
[4] POST /queue/tag line=1 check=1 -> HTTP 302, loc=/queue?tagged=1
    cost_checked: 0 -> 1   *** WRITE SUCCEEDED ***
```

Reported defect against the approved design: the skill and PRD R2-1..R2-3 state the check is
**final** and only a Cost Controller may perform it. This route lets a Viewer perform it, which
**writes directly into `v_cbs_actual`** — the cost report. It also collaterally bypasses the SoD
predicate (`checkSoD` is not called on this path).

### B3 — The import endpoints (which write the ledger) require only a session

`src/routes/api.js:72/120/132` all use `requireAuth` — **not** `requireCapability`. The import path
writes `accounting_ledger` rows directly.

**Proven:** a Viewer staged and confirmed a CSV, posting a real cost line:

```
POST /api/imports               as Viewer -> HTTP 201  (staged, ledger untouched — correct)
POST /api/imports/1/confirm     as Viewer -> HTTP 200
  ledger rows: 6 -> 7   *** VIEWER WROTE LEDGER ROWS ***
  inserted: {"id":7,"amount":888000,"description":"viewer staged import","source":"import"}
```

Note the staging step correctly does **not** write the ledger (good layering) — but confirm does,
and confirm is unguarded.

### B4 — Detected: five unguarded mutating routes, in order of blast radius

| Route | Guard today | Effect for a Viewer |
|---|---|---|
| `POST /ledger/:id/reverse` | none | irreversible correction on a real line |
| `POST /ledger/entry` | none | invents cost / income in the book of record |
| `POST /api/imports/:id/confirm` | `requireAuth` | bulk-posts arbitrary cost lines |
| `POST /queue/tag` | none | final cost check + CBS assignment → moves the cost report |
| `POST /api/imports` (stage) | `requireAuth` | stages arbitrary files (10 MB each) |

### B5 — `synchronous = NORMAL` contradicts the binding spec

`src/db/db.js:11` sets `PRAGMA synchronous = NORMAL`. **TECH-SPEC §4.1 requires `synchronous=FULL`**
for this file (SQLite durability). Under WAL + NORMAL, a power loss or OS crash can **lose
already-committed transactions** (it will not corrupt the DB — that distinction is WAL's, not
NORMAL's). For a financial book of record this is the wrong side of the trade, and the spec already
decided it. Verify: `PRAGMA synchronous` on a fresh connection returns `1` (NORMAL); `2` is FULL.

## Verified good (do not "fix" these)

- **Money invariants are DB-enforced, not app-enforced**: `trg_ledger_money_integrity_insert`
  (whole rupiah, `amount = debit − credit`, one side only), `trg_lpb_money_integrity_insert`,
  `trg_cash_advance_money_integrity_insert`. App bugs cannot produce an invalid amount.
- **Immutability is real**: `trg_ledger_no_delete`, `trg_ledger_no_amount_update`,
  `trg_ledger_immutable_financial_fields`, `trg_ledger_reversal_must_negate`,
  `idx_ledger_one_reversal`, plus `trg_audit_log_no_update` / `no_delete`. The audit trail cannot
  be rewritten even by direct SQL.
- **Time handling is correct and unusually careful**: all session expiry/idle comparisons are done
  as `strftime('%s', …)` epoch integers inside SQLite, never by parsing SQLite's timezone-less
  `datetime('now')` into a JS `Date`. That is a genuinely subtle bug, correctly avoided and
  documented in the file header.
- **CSRF is sound**, including the multipart header path (`x-csrf-token`) that keeps the import
  upload protected where `express.urlencoded` cannot see the body.
- **Auth is solid**: Argon2id with legacy-hash auto-upgrade, timing equalizer (`pwd.burn()`),
  generic errors that do not leak account existence, session fixation handled by minting a new
  session at login, `revokeUserSessions` on disable/role change.
- **Index coverage is good**: 11 indexes on `accounting_ledger`, and `EXPLAIN QUERY PLAN` confirms
  the ledger list query uses `idx_ledger_period`.
- **Dedupe index is correct and partial**: `idx_ledger_import_dedupe … WHERE source='import'`, so
  manual duplicates stay legal while re-imports are refused.
- **The three-outcome checker (Check / Return / Block)** with `superseded_by` is a better model than
  the spec's original two outcomes, and its guards are trigger-backed.

## Test-strategy gap (the root cause)

`grep 403 test/*.test.js` shows authorization is asserted in **exactly one area**:

- `admin.test.js` — 4 assertions that a non-administrator is denied `/admin/users` ✅
- `advances*.test.js` — several capability assertions ✅ (module 5 was built test-first)
- **`entry`, `queue`, `import`, `correct`, `csrf`, `auth`, `scaffold` — zero authorization assertions.**

`correct.test.js:241` (`C4.2 reversal needs a session and a CSRF token`) is the closest thing, and it
tests **anonymous** (403 via CSRF middleware) and **tokenless** — never *an authenticated
low-privilege user*. That is precisely the gap B1–B3 live in.

**Required pattern going forward** — for every mutating route, assert all four:

1. anonymous → redirect/401,
2. no CSRF token → 403,
3. **wrong role (authenticated Viewer) → 403, and assert the DB row count is unchanged,**
4. correct role → succeeds.

Step 3 is the one that has been missing, and step 3's **row-count assertion** is what makes it a
security test rather than a status-code test.

**Recommended response:** treat B1–B3 as one remediation slice (the fix is small — add capability
flags and guards, plus the missing tests) **before** any new feature work. Every new route added on
the current pattern inherits the same omission, and modules 7–9 add a dozen more mutating routes.
